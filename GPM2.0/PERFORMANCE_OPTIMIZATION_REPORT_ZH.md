# GPM 2.0 性能优化报告

更新日期：2026-09-18  
覆盖范围：Server `--reads` 质控、GRT Server、App 染色体切换与大视图渲染

## 1. 结论

本轮优化已解决 `--reads` 阶段最明显的三个耗时来源：默认流程不再执行 CRAQ、多个 reads 数据集可以并行处理、重复运行可以按数据集复用缓存。Meryl、Merqury 以及代码中保留的 CRAQ 完整模式均会受到统一线程预算控制，避免多任务并发时线程过量。

用户报告中的旧流程在 16 线程下，仅 GRT prepare/read QC 就耗时 **17,955.866 秒（4 小时 59 分 15.866 秒）**，随后还因 CRAQ 输出目录中的外部软连接而失败。该数据是本轮优化前的真实基线。优化后的同机、同数据实测尚未执行，因此本文不会用估算值冒充最终提速结果。

此前完成的优化已有以下可复核实测：

| 模块 | 优化前 | 优化后 | 提速/降幅 | 数据口径 |
|---|---:|---:|---:|---|
| GRT 合同数据重复校验 | 约 7 分 31 秒 | 31.59 秒 | 约 14.3 倍；耗时降低 93.0% | 同一 Server 工作区重复读取 |
| `finalize_evidence` | 430.517 秒 | 37.412 秒 | 约 11.5 倍；耗时降低 91.3% | 同一真实 Server 工作区 |
| App 染色体切换核心数据读取，首次访问 | 约 1.50 秒 | 约 0.37 秒 | 约 4.1 倍；耗时降低 75.3% | `gs3` 工作区，不含前端渲染 |
| App 染色体切换核心数据读取，再次访问 | 约 1.50 秒 | 约 0.02 秒 | 约 75 倍；耗时降低 98.7% | `gs3` 工作区，命中参考序列几何缓存，不含前端渲染 |

## 2. `--reads` 阶段优化

### 2.1 用户报告中的真实基线

基线来源：

- `D:\Desktop\报错.txt`
- `D:\Desktop\zyr-test4-test.report.html`

运行参数包含 `--reads` 和 `-t 16`。主要输入规模如下：

| 输入 | 大小 |
|---|---:|
| 参考基因组 | 390,532,154 bytes |
| Primary assembly：`pre.fa` | 386,211,102 bytes |
| Support assembly：`assembly.fasta` | 394,350,078 bytes |
| ONT reads：`ont_30x.fastq.gz` | 11,798,815,740 bytes，约 11.8 GB |

报告记录的阶段耗时：

| 阶段 | 耗时 |
|---|---:|
| Primary 对参考序列比对 | 105.905 秒 |
| Support 对参考序列比对 | 88.520 秒 |
| 序列归属计算 | 41.680 秒 |
| GRT prepare/read QC | **17,955.866 秒** |

read QC 占这组已记录耗时的绝大部分。旧流程结束前还执行了 CRAQ，并在终端输出校验时发现：

```text
grt/qc/assembly/craq_output/assembly/ont_30x.fastq.gz
```

该路径是指向工作区外部输入的软连接，导致安全校验失败。也就是说，用户等待约 5 小时后仍未得到成功结果。

### 2.2 旧流程的耗时原因

旧实现存在以下问题：

1. 只要传入 `--reads`，每个 assembly 都会完整执行 Meryl、Merqury 和 CRAQ。
2. 多个 assembly 按顺序执行，空闲 CPU 不能用于处理其他数据集。
3. Meryl 没有获得完整的全局线程预算；Merqury/CRAQ 的内部线程也没有统一限制。
4. 相同输入重复执行时，已有 QV 和 CRAQ 结果不能按数据集稳定复用。
5. CRAQ 把 reads 软连接写入输出目录，既增加流程复杂度，也会触发 Server 的工作区边界校验。

### 2.3 已实施的优化

#### 默认流程精简

公开的 `--reads` 流程现在只执行 Meryl + Merqury，用于计算每个 assembly 的 QV。默认流程不再执行 CRAQ，也不再依赖 CRAQ 生成的结果。

CRAQ 完整流程仍保留在代码中，供内部兼容和专项验证使用，但不作为 README 中的公开使用方式。

#### 多数据集并行

不同 assembly 的 reads QC 任务由线程池并发调度。总线程数仍由 `--threads/-t` 控制，并在待处理数据集之间分配：

- 16 线程、2 个待处理数据集：每个数据集 8 线程。
- 32 线程、3 个待处理数据集：分别分配 11、11、10 线程。
- 只有 1 个待处理数据集：可以使用全部可用线程。

实际线程预算还会受进程 CPU affinity 限制，因此不会假定服务器上所有逻辑 CPU 都可用。

#### 工具内部线程控制

- Meryl 使用分配给该数据集的完整线程数。
- Merqury 通过 `OMP_NUM_THREADS` 和 `OMP_THREAD_LIMIT` 使用相同预算。
- 内部 CRAQ 完整模式同时设置 OpenMP 上限，并通过 `-t` 传入对应线程数。

这样可以同时利用“数据集之间的并行”和“单个工具内部的并行”，并防止每个并发任务都私自占满全部 CPU。

#### 按数据集缓存

Meryl、Merqury 和内部 CRAQ 模式都建立了带输入哈希校验的缓存：

- 输入和参数未变化时，直接复用该数据集的有效结果。
- 只有发生变化或缓存损坏的数据集才重新计算。
- 复用结果时优先创建硬链接；文件系统不支持时自动回退为复制。
- 缓存是按数据集隔离的，一个数据集失效不会迫使其他数据集重算。

这项优化对调参、失败重试和相同数据的重复运行最明显。首次冷运行仍需要完成 Meryl/Merqury 的实际计算。

#### 软连接处理

Server 的 CRAQ 检查点收集现在会忽略 CRAQ 创建的外部输入软连接，并清理旧检查点中的此类条目，避免再次出现“计算已经完成，但最终因输入软连接越界而失败”的情况。

### 2.4 预期效果与当前结论

本轮改动的确定性收益如下：

- 默认 `--reads` 不再承担 CRAQ 的运行时间。
- 多个 assembly 不再完全串行执行 read QC。
- 单数据集可充分使用用户指定的线程预算。
- 重复运行命中缓存时，可跳过对应数据集的 Meryl、Merqury 和内部 CRAQ 计算。
- CRAQ 的外部 reads 软连接不会再使最终校验失败。

实际加速倍数取决于 assembly 数量、磁盘吞吐、reads 压缩读取速度、可用 CPU 和缓存命中情况。当前没有优化后对上述 11.8 GB reads 的同机复测数据，因此不能把理论并行度直接写成实测倍数。

### 2.5 验证情况

代码层面已经完成以下验证：

- reads QC 定向测试：9 项通过。
- Server 完整质量门：122 项 Python 测试、全部 shell 测试和端到端测试通过。
- 覆盖默认跳过 CRAQ、线程预算分配、Merqury/CRAQ 线程环境、缓存命中、单数据集失效重算以及软连接清理。

建议使用用户原始数据补充一次性能验收：

1. 在同一服务器、同一存储、同一软件环境中使用相同输入和 `-t 16`。
2. 使用全新工作区执行一次默认 `--reads` 冷运行。
3. 原样重复一次，记录缓存命中的热运行。
4. 从 `logs/status.tsv` 和工具日志记录总耗时、各阶段耗时、峰值内存和 CPU 使用率。
5. 对比 QV 输出及核心结果文件哈希，确认提速没有改变应保留的结果。

## 3. 此前完成的 Server 提速

### 3.1 GRT 合同数据缓存

Server 的后续阶段过去会反复解析和校验相同的 GRT 合同数据。现在把稳定的读取结果缓存在工作区内，并在输入契约变化时失效。

真实工作区测量结果：

- 合同校验：约 451 秒降至 31.59 秒，约 14.3 倍。
- `finalize_evidence`：430.517 秒降至 37.412 秒，约 11.5 倍。
- 优化后通过 119 项相关测试。

### 3.2 GRT Step2/3 并行与分区复用

真实 Server 冷运行曾记录：17 个阶段总耗时约 1 小时 26 分，其中 Step2/3 为 3,859.98 秒（约 64 分 20 秒），是当时主要瓶颈。测试数据约 273.73 Mb、986 条序列。

现有实现提供：

- `prepare.sh --threads/-t N` 把线程数传递到生成的 Step2/3 工作流。
- MUMmer 分区并行执行；worker 数同时受用户线程数、CPU affinity、分区数量和内存约束。
- 每个 `nucmer` 分区任务只使用一个线程，避免多层并行造成过量占用。
- 有效分区结果可复用；零命中的合法 header-only delta 也能被准确识别和缓存。

3,859.98 秒是冷运行中的瓶颈测量值，现有材料没有同机、同输入的改造前后成对总时长，因此这里只记录已实施机制，不声明未经测量的 Step2/3 加速倍数。

### 3.3 参考片段扫描

参考片段扫描已改为更高效的实现，减少大参考序列上的重复扫描工作。该项已有代码和回归测试，但没有保留可用于报告的同机前后耗时，因此不写推测性数字。

## 4. 此前完成的 App 提速

### 4.1 染色体切换

染色体切换时，primary、history、phased、reference、support、deleted 和 detail 等相互独立的数据读取现在并行执行。参考序列几何数据使用有界缓存，缓存键包含文件路径、大小、修改时间和染色体，避免输入变化后误用旧结果。

请求和工作区切换还增加了过期结果保护：较慢的旧请求返回后不能覆盖用户已经切换到的新染色体或新项目。

`gs3` 工作区实测的核心读取耗时：

- 优化前约 1.50 秒。
- 首次访问约 0.37 秒，约 4.1 倍。
- 再次访问约 0.02 秒，约 75 倍。

这些数字只统计核心数据读取，不包含浏览器渲染；优化前后输出哈希一致。

### 4.2 大视图刻度渲染

Subview 标尺刻度已采用虚拟化渲染，只生成当前可见区域所需的刻度，避免染色体或 contig 很长时创建大量无效 DOM 节点。该项主要改善大视图的响应性和内存占用，目前没有纳入统一计时基准。

## 5. 使用和评测注意事项

- 冷运行和缓存命中运行必须分开报告，两者不能直接混为一个“平均耗时”。
- 多个大数据集并发时，磁盘吞吐可能先于 CPU 成为瓶颈；需要同时观察 CPU、I/O 和峰值内存。
- CRAQ 内部仍包含不能完全并行的步骤，内部完整模式的加速不会与线程数线性增长。
- 输入文件、关键参数或工具版本变化后，相关缓存应失效并重新计算。
- 已生成的旧 Server 工作区包含旧版脚本。更新代码后，应重新生成工作区，或重新运行新版 `prepare.sh --threads N`，不能只替换最终执行入口。
