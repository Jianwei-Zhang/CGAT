# Server job 产出：直接取 FASTA，一个项目一对 App 包

2026-11-23 · 设计约定 / 实施中。直接在 `master` 推进，设计基线 `d0a6d367`。本文描述新建 job 的目标，不是已发布版本的使用说明。既有编号布局和旧交付包继续按原协议读取；不自动迁移、不移动客户数据。报告页面的内容、样式由独立分支负责。

## 用户从哪里拿结果

以 `--out runs/col0` 为例，首次创建时保存目录名 `col0` 作为文件前缀。改目录名或续跑不改变它，不新增前缀参数。下列是发布后的示例，不要求未运行的工具生成占位文件：

```text
04_refinement/
  automatic/<tool>/                  # 输入、尝试与回执、原生工作目录、接纳的来源和证据
  manual/<batch>/                    # 任务快照、各位点/工具记录、诊断；不是交付包的第二个副本
05_final/
  col0.lgz.fa                        # 可选精修之前的 LGZ 全基因组
  col0.degap.fa                      # 各已发布工具独立出 FASTA，不串联，也不选“最佳”
  col0.manual-<batch>.fa             # App 导出时整套组装 + 本批接纳的修改
  results.tsv                        # 简表；无需浏览器即可判断哪个文件能用
  details/                           # Final Path、sources.tsv、剩余缺口和来源凭据，按版本区分
06_report/                           # 总览入口 report.html；详细解释留在报告
07_delivery/
  col0.full.tar.gz                    # 新建项目，项目级唯一一对；选择 zip 时沿用该格式
  col0.light.tar.gz
  col0.auto.patch.zip                # 追加自动精修版本；LGZ-only 时不存在
  manual/col0.manual-<batch>.patch.zip  # 每个手动批次一个；文件名带批次，不再嵌套一层
.runtime/                            # 私有运行状态，不是可整删的临时目录
```

`01_inputs/`、`02_alignments/`、`03_lgz/` 保留各自职责；不再另设顶层 `08_refinement_jobs/`。`<batch>` 是稳定的批次标识，与相应 FASTA 相同；文件名不是身份证明，完整身份与内容摘要写入包内。不同批次、不同内容不能因短标识相同而覆盖。新 job 不做无用途的目录占位或旧路径影子树。

`results.tsv` 区分**本次尝试**与**当前可用发布**。最低信息为版本/工具或批次、尝试状态、已接纳数、可用 FASTA 相对路径和对应发布身份。成功但零接纳仍有该版本的 FASTA，标注与其起点相同；工具失败而有上次成功时列出旧文件来自哪次发布，不冒充本次成功。LGZ 成功后始终有基线可取；从未成功则据实报错，不伪造 FASTA。不存在会在不同工具之间悄悄换指向的 `final.fa`。

## 三种运行，三种交付规则

| 工作区发生什么 | 项目 Full / Light | 累计自动补丁 | 手动补丁与 FASTA |
|---|---|---|---|
| 首次只发布 LGZ | 生成同一代的一对 | 无 | 无 |
| 补跑自动精修 | 自动可交付版本新增或内容改变才成对更新，保留 LGZ 和其余版本 | 更新同名 ZIP，独立从 LGZ 导入即可补齐，不需找齐前几轮 | 不改 |
| 自动续跑命中相同结果，或本轮没有新的成功结果 | 不重打，摘要不变 | 不重打 | 不改 |
| 运行 App 导出的手动批次 | 不重打，两个摘要不变 | 不重打 | 每批一个 ZIP、一份完整 FASTA；不因工具多而多发包 |

不要原地修改已公开归档。先校验新一代所需文件、Full/Light 的版本集合、自动补丁与 FASTA 的来源，再提交发布回执；中途失败仍只认可上一整代，不能让读取者把新 Full、旧 Light 拼成成功。修复或重复导入同一代不得产生重复版本。Full 含序列，Light 不承诺离线导出不可用的来源序列；两者表示相同的版本、路径与测量证据。LGZ-only 不产生空的公开比较批次；运行过精修则保留必要状态，包括失败及零接纳。与报告分支约定相对路径、版本身份和清单/回执，本项工作不重做 HTML。

## App 中共存的是版本，不是多套各自建项的包

- 不论有几个自动工具，导入时一律不弹版本选择，包中所有已发布工具结果连同 LGZ 基线一起进入项目。只有一个工具时可直接使用它；已有项目追加工具时保留当前工作路径和人工编辑。多工具独立结果不等于一条逐 Gap 合并的组装，不能用手动工具优先级、运行先后或闭合数量替用户覆盖工作路径。
- 查看另一版不改变工作版本。导出 FASTA、AGP、手动任务沿用已选工作版本，不重复弹窗；只有显式切换才改变来源。项目页精修卡用一张表展示自动工具与手动批次；自动工具分别列出闭合、部分填补、未填补、拒绝和接纳改动，不把涉及缺口数当作闭合数，旧数据没有的统计显示为未知。补丁导入在卡片右上角，使用带文字提示与无障碍名称的图标。各版本独立保存人工编辑、撤销记录和任务归属；相同染色体名/位点名不是跨版本应用依据。
- 同一补丁导入入口按**包内协议与内容**识别两类 ZIP，而非按文件名。自动补丁绑定 LGZ 基线、Final Path 与来源身份，携带新增来源序列、各工具路径和测量证据；给匹配的已有项目增加版本，不覆盖其工作路径、无关编辑或自动切换。已存在相同内容则跳过，同工具有新代也不能覆盖依赖旧代的编辑。错误基线、残缺或篡改的包整体拒绝。
- 手动补丁绑定原 App 项目、工作版本、导出批次和目标边界。回导前核对当前位置和来源，不因无关编辑而拒绝，也不因表面坐标相同而覆盖变动位点。新建项目的整包与回到原项目的位点补丁不可互相冒充。

## 手动精修：一个 Gap 一个任务，任务内可多选工具

1. 新建 Gap 任务**默认只勾 DEGAP**，同一任务可加选其他工具；不同 Gap 独立配置。左右端粒继续用 DEGAP TelSeeker，按端点校验延伸，不与补洞比较。任务包绑定点击导出时的**全项目**工作版本快照，即使只请求 Chr3 的一个 Gap，Chr1 以前的人工修改也必须保留。记录每条 Final Path 与来源摘要，复用 Server 已有且内容匹配的序列，只随包携带必要的 App 独有序列，不复制公共 reads。
2. 对同一 Gap，先校验闭合与边界；合格闭合候选有多个，再按 **DEGAP → LR_Gapcloser → TGS-GapCloser → quarTeT** 采用一个。部分填补不压过完全闭合；没有闭合则保留原片段。此顺序用于同一手动位点的择优，不用于自动版本排序。候选和原因留档；端粒成功单独统计。
3. 各工具均结束或明确失败后按位点结算，一个失败不扣住同批其他合格结果。Server 用同一份逐位点选择清单生成整套手动 FASTA 与补丁；如原项目未继续编辑，回导再导出的序列应与 Server 逐染色体一致。零接纳的起点是导出时的快照，不一定等于 LGZ。缺少或不匹配的必需来源明确报错，不发布残缺或以 LGZ 替代的整基因组。迟到的更高优先级或改了内容的重跑不能静默覆盖已交付批次或 App 已采用位点。
4. 老任务包没有完整快照时仍可按原协议处理局部补丁，不用局部材料推算全基因组。新 App 仍能读取旧项目包、旧回传凭据；新协议有清晰的版本边界，不让旧读取器把多版本包当单版本成功导入。

## 清理边界与已有代码的衔接

用户提供的 180/col0 历史盘点中，`04_refinement` 约 11 G，多数为原生工作现场；精修 staging 中终版约 444 M、归档副本约 722 M。它们是两类问题：**挪目录不会释放这 11 G**；历史大小也不是本次优化的实测节省量。默认保留原生工作现场，另提供用户显式瘦身，先说明会失去哪些诊断或免重算路径。接受的序列、测量证据和仍被任何发布/历史版本引用的来源不属于普通缓存。

- `.runtime` 中锁、工作区布局与运行元数据、checkpoint、发布回执、恢复中的事务必须留存。发布成功后改用正式结果作权威来源，才可回收已验证可替代的 staging。LGZ 从 Full staging 派生 Light 的读路径和重新打包/失败恢复均要一起验证，不能在写端直接加递归删除。报告只消除同一已发布站点的多余构建副本，不破坏失败诊断、离线浏览或包内必要文件。
- [现有布局解析](../server/tools/workspace_layout.py)、[发布事务](../server/tools/refinement_commit.py)、[缓存查找](../server/tools/refinement_cache.py)和[原生回执](../server/tools/refinement_native_checkpoint.py)仍以旧版路径为契约。新布局要显式标记，按版本解析；旧工作区原地读取/续跑，不因新版二进制启动而重排。
- [现有归档构建](../server/tools/refinement_bundle.py)和 [App 读取](../app/backend/src/grt_package/refined_delivery.rs)按单工具校验；不能把多套旧包简单套进一个 ZIP。[手动任务导出](../app/backend/src/degap_jobs/manual_refinement.rs)、[Server 执行](../server/tools/refine_run.py)和[回导](../app/backend/src/degap_jobs/manual_refinement/apply.rs)分别负责快照、候选和落到原路径，三端都需形成一致的版本/位点边界。

## 已验证的进度（不替代上面的整体验收）

- **手动 Gap 工具多选**：同一位点只登记一次，默认 DEGAP，可同时选择其他工具。勾选、取消、保存后重读、全项目预览和实际任务 ZIP 均保留完整工具列表；端粒仍固定用 TelSeeker。回导的四位点受控测试覆盖双闭合择优、一工具失败而另一工具闭合、全部部分填补、低优先级完全闭合胜过高优先级部分填补，并按实际采用的补丁重建 FASTA。该测试使用构造的工具结果，不是四种原生工具实跑，也不是新布局下的整基因组快照验收。
- **Server 直接 FASTA 与结果清单**：新 job 的 `05_final/` 已按创建时前缀发布基线和工具结果；清单绑定正式发布与本次尝试，回归覆盖旧编号工作区、补跑失败保留旧发布、损坏拒绝和中断恢复。项目级多版本归档与自动补丁是后续协议，不由本条验证。
- **项目精修卡与效果数据**：Full/Light 导入时，从校验过的逐原始缺口结局保存该工具的统计；同一表格可列多个工具与手动批次，右上角图标保留原有回导、归属检查和撤销入口。受控用例区分真实零、部分填补和旧项目未留存指标。现有单工具包的真实导入和多行表格渲染已分别验证，不等于项目级多工具交付包已实现。
- **累计自动补丁**：Server 从已发布工具结果生成一份同名 ZIP，仅携带受接纳的新来源序列、版本路径与证据。受控 Server → App 回归验证从 DEGAP 追加 TGS 后，仅导入最新 ZIP 即得到两版；已有编辑保留、重导不重复、错误基线和损坏 ZIP 整体拒绝。此项不是项目 Full/Light 或版本切换的验收。

### 手动批次的整基因组（代码已接入，待安装验收）

从项目级 Full 或 Light 导出手动任务时，`refinement_tasks.zip` 的 v2 清单绑定一份单独的 `assembly_snapshot.json`。即使只选一个 gap，快照也记录整套工作路径的染色体、顺序、片段方向和来源；有 Server 来源的片段只记内容凭据，只把 App 独有的区间随包携带。无快照的旧任务继续只发局部补丁。Light 中若连必要的身份或来源序列都不可用，明确报错，不用 LGZ 序列补位。

正常运行 `python .lib/tools/refine.py <任务包>`：`05_final/<out>.manual-<16位批次>.fa` 是可直接使用的全基因组；`results.tsv` 追加该批次；`05_final/details/manual-<16位批次>/selection.json` 说明每个位点采用哪个工具，并记录各染色体摘要。一次批次只发一份 `07_delivery/manual/` 补丁，不改项目 Full/Light 或累计自动补丁。Server 和 App 使用相同的完整闭合优先规则；App 回导仍需检查当前位点边界。零接纳的 FASTA 对应导出时的工作路径，不是重新拷贝原始 LGZ。以上是接口及实现说明，不是运行验收记录。
