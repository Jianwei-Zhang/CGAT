## 1. 目标与工作边界

用户运行一次 Server 流程，即可在 LGZ 后继续使用 reads 精修剩余 gap；已经完成 LGZ 的工作区也能追加这一步，不重新计算 LGZ。用户能从 `--out` 目录直接找到每个阶段、每种工具的最终结果和完整报告。

精修不是附带一份额外 FASTA。启用精修后，Final Path、最终 FASTA、App 导入及再次导出的序列必须对应实际接纳的精修结果。原始 LGZ 结果单独保留作基线。

## 3. 用户入口与默认规则

### 3.1 新工作区

```bash
# 提供 reads，默认接 DEGAP；HiFi、ONT 不要求同时提供。
bash "$SERVER/run.sh" --ref ref.fa --ds assembly.fa \
  --hifi hifi.fastq.gz --ont ont.fastq.gz -o workspace

# 指定单个工具。
bash "$SERVER/run.sh" --ref ref.fa --ds assembly.fa \
  --hifi hifi.fastq.gz --gapfill-tools lrgapcloser -o workspace

# 多工具分别处理同一份 LGZ 基线，不串联。
bash "$SERVER/run.sh" --ref ref.fa --ds assembly.fa \
  --hifi hifi.fastq.gz --ont ont.fastq.gz \
  --gapfill-tools degap,tgsgapcloser,quartet,lrgapcloser -o workspace
```

- 唯一工具选择参数为 `--gapfill-tools`，不增加 `--final-tool`。
- 工具标识为 `degap`、`tgsgapcloser`、`quartet`、`lrgapcloser`；`none` 显式关闭本次精修。
- 新任务没有 reads 时只做 LGZ；提供 reads 且未指定工具时默认 DEGAP。
- 已有精修任务续跑时，未再次提供 reads 使用该任务保存的输入，不能把它解释为关闭精修。
- 显式选定工具但没有可用 reads 时提前报错；不能静默跳过。
- `none` 不与工具列表混用，不删除历史精修结果。
- 多个 reads 文件和重复的 `--hifi` / `--ont` 继续支持；保留文件的类型、次序和内容身份。

### 3.2 已完成 LGZ 的工作区

```bash
cd workspace
bash run_all.sh --hifi /data/hifi.fastq.gz --ont /data/ont.fastq.gz

# 后续追加其他工具，不重跑有效 LGZ 或已经完成的同配方精修。
bash run_all.sh --gapfill-tools degap,tgsgapcloser,quartet,lrgapcloser
```

新增 reads 是登记下游任务，不是修改原始 LGZ 输入。不能为此放松原 LGZ 的输入一致性检查，也不能重新 prepare 覆盖工作区。

相同配方与有效输出复用结果；变更 reads、工具内容或参数建立新运行记录，不覆盖或冒用旧结果。旧工作区必须先经过第 8 节的布局迁移。

## 4. 四工具与 reads 分配

| 工具 | 两类 reads 均提供时 | 单一类型提供时 |
| --- | --- | --- |
| DEGAP | 原生 HiFi + ONT 混合模式 | 使用所提供类型 |
| quarTeT GapFiller | 转换为 FASTA 后以多个输入单次运行 | 使用所提供类型 |
| TGS-GapCloser | 只使用 HiFi，单次运行 | 使用所提供类型 |
| LR_Gapcloser | 只使用 HiFi，单次运行 | 使用所提供类型 |

- 用户直接提供 `--hifi` / `--ont`，不增加必须先纠错、证明已纠错或另交纠错文件的门槛。
- 必要的 FASTA/FASTQ、压缩格式转换由 CGAT 完成；输入文件本身保持不变。
- 仅执行选定固定配方中的工具处理步骤，不暗中新增一套外部 reads 纠错流水线。工具自身的纠错步骤应记录在报告中。
- HiFi 优先是已确认的输入选择规则，不是声称另两款工具不支持 ONT，也不是测得的质量或性能结论。
- 同一工具不因同时提供两种 reads 自动拆成两个运行。
- quarTeT 多输入使用其原生通路，不冒称与 DEGAP 分类型混合算法相同；比对配方须通过测试。
- 每个结果记录实际使用和未使用的 reads 及原因。不同实际输入的结果不表述为严格控制变量比较。
- 派生 FASTA 的序列名处理要保留原文件、原 ID、类型的可逆对应，防止跨文件同名覆盖。

## 6. 精修接纳与 Final Path

### 6.1 结果不是整条原生 FASTA 的无条件替换

每个工具独立从同一份冻结的 LGZ 基线运行。原生候选和原生整合结果保留，CGAT 另行生成可追溯的精修路径。

允许接纳：gap 填补、两侧重叠闭合、明确报告的邻近 gap 联合修复，以及部分修复。不能继续只接受正长度桥接、拒绝一切重叠和联合修改。

每项改动需要绑定：原始 gap 身份、原始坐标与替换范围、工具任务、候选序列及来源、参数版本、接纳理由与结果坐标。跨多个 gap 的修改保留各原始 gap 的对应关系；不能跨工具混合候选。

不能可靠解释的改动作为未接纳候选保留，明确原因。退出码成功、N 数减少或两侧结构一致，均不单独等于生物学正确性已验证。

部分修复可进入 Final Path，尚未解决部分仍是 gap。完全闭合、部分修复、未修复和候选未接纳分别统计，不重复计数。

### 6.2 发布链路与不变量

```text
冻结 LGZ 基线
  → 工具运行与原生结果
  → 改动归一化、来源登记与接纳
  → 构建每个工具的精修 Final Path
  → 按路径重建最终 FASTA
  → 更新受影响的比对、注释、坐标和统计
  → 原子发布最终结果、报告和 App 包
```

**核心不变量：Server Final Path 重建的序列 = `05_final/<tool>/assembly.fa` = App 导入后导出的 Final Path 序列。** 按染色体序列内容比较，不依赖 FASTA 换行格式。

- 未改变的 LGZ 片段保留原来源；切分片段保留父片段关联及正确方向、区间。
- 新桥接或修改片段登记真实的精修序列来源，不把整条染色体伪装成一个没有细节的精修来源。
- 正确处理长度改变、负链来源、重叠闭合、剩余 N 和后续片段坐标位移。
- 失效的旧坐标、比对、注释和统计不可随新 Final Path 直接交付；重建必要内容并标明证据来源。
- 精修完成但接纳零处时，最终序列允许与 LGZ 相同，状态写明“精修完成，接纳 0 处”。
- 精修失败或结果不完整时，不把 LGZ 复制为该工具的成功结果。LGZ 基线仍可查看和单独交付。
- 工具原生结果、CGAT 接纳结果及差异都保留，避免比较表只反映包装层限制。

## 7. 执行、重试与报告

- LGZ 是各精修任务的共同前置条件。工具之间默认顺序执行，每个工具使用同一份总线程预算；内部 job 并发也受该预算约束。
- 沿用用户现有调度作业，不自动提交额外集群任务。
- 精修分支相互独立。单工具失败不阻止其他工具，成功分支正常发布；汇总状态为部分失败，进程返回非零。
- 续跑优先复用已验证完成的阶段和子结果。缓存绑定实际输入、配方、工具内容、基线和输出，不凭裸退出码或遗留文件存在判断成功。
- 中断和发布失败可恢复，旧成功结果及原始 LGZ 不被破坏。配置改变属于新运行，不伪装成原任务续跑。

报告导航为：总流程 → 工具 → 原始 gap → job/日志/原生报告 → 候选与接纳决定 → 最终序列。

报告包括输入、版本、参数、运行状态、耗时和资源记录、原始 gap 对照、完全闭合、部分修复、未解决及未接纳原因。计数分母始终能追溯到同一 LGZ 残余 gap 清单；工具未尝试的目标不能从比较中消失。

不在没有独立真值时生成准确率或自动评选最佳工具。后续独立比对/质量评估可加入，不能用 gap 更少替代正确性证据。

HTML 和原生报告入口随交付物可搬移，使用安全的相对链接。完整包和轻量包明确哪些序列可用、哪些需补充，不提供失效的本机绝对路径链接。

## 8. 旧工作区迁移与 App 协议

### 8.1 工作区迁移

新版入口先识别布局版本。旧目录追加精修前，先只读检查并展示迁移摘要，通过一次明确迁移操作升级；此后按正常命令续跑。

迁移须覆盖：运行脚本、输入和来源索引、持久化相对/绝对路径、执行计划、检查点、报告、最终结果与打包配置。不能只做目录重命名。

- 获取工作区独占锁，拒绝正在运行的工作区；不得仅凭锁文件存在/不存在推断跨节点作业已停止。
- 记录迁移前清单、校验值、版本和事务进度，准备恢复路径。
- 保留有效 LGZ 与比对结果，不重新 prepare，不因路径改变丢弃内容有效的完成证据。
- 迁移中断可恢复，校验通过后才提交新布局版本。
- 老 runtime 不会识别新参数时，提供新版已安装 Server 的明确迁移入口，而不是要求用户先运行无法识别参数的旧脚本。
- 具体迁移命令及物理路径映射表在实现时一并固定到测试和用户说明，不能依赖临时手工搬运。

完成 LGZ 的旧目录已有显式迁移入口，未完成任务增加经过内容审核的原引擎前缀续跑，再独立审批物理迁移，见 [迁移契约](server-refinement-migration-contract-20261122.md)。原引擎冻结基线与新引擎缓存分开，不重写旧科学回执。受控脚本与缓存边界检查不能代替真实未完成旧阶段、历史版本和终止场景的最终验收。

### 8.2 App 导入

升级交付协议与 Final Path 协议，包含精修来源、桥接序列、改动关联及每个工具独立的最终路径。

- 每工具分别生成完整包与轻量包，导入为独立项目；本轮不增加单项目多套 Final Path 切换编辑。
- 新版 App 继续识别旧包，旧包仍表示原 LGZ 结果。
- 新包不得悄悄回退到旧 LGZ 路径；不支持新协议的旧 App 必须明确拒绝或提示升级，不能部分成功。
- 完整包携带重建精修路径必需的序列；轻量包保留相同路径、身份和来源契约，序列未就绪时不能假装完成序列级验证。
- 用户已经人工编辑的 App 项目不因协议迁移或新结果导入被覆盖。新结果导入和已有项目存储升级是两件事。

## 9. 环境、版本与依赖更新

四种工具通过同一个 Server 安装入口提供。默认运行 DEGAP 不等于只安装 DEGAP。

维护 `cgat-server.conda-spec.txt`、`cgat-server.linux-aarch64.conda-spec.txt`、平台锁定清单、`env.sh` 检查及固定工具来源清单。能由环境管理器提供的依赖统一管理；其他源码/二进制由安装器按固定内容部署，不要求用户另装三个环境。

- 不为迁就新工具随意降低现有 Python、minimap2、samtools 的核心版本。
- `install.sh --check` 检查实际工具版本、内容来源、必要模块和最小运行能力，不只检查命令存在。
- 分别验证 x86_64 和 ARM64；依赖求解成功不等于工具可执行，noarch 包也不证明上游附带二进制跨架构可用。
- 环境升级由安装入口完成；`run_all.sh` 中途不自动安装/替换环境，不影响正在共享使用它的任务。
- 工具升级不把旧运行冒充为新版本结果；运行与结果记录保留实际版本。
