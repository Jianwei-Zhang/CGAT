# Codex 独立验收规范

验收对象是 Claude Code 的实际实现和运行结果。文档审阅通过不等于功能验收通过。
当前所有功能验收项均为待执行；由 Codex 在实施交接后执行并填写结果。

## 1. 验收输入

Claude 提供实施提交、输入/工具/运行库哈希、基线、off/audit/apply 产物、回归比较器、chr10 证据和 tests/CI 日志。
Codex 首先核对工作树、提交范围、基线身份和实验目录可读性；不能只接受 Claude 的文字总结。
独立抽取原始证据并重算关键区间、长度、源序列和接头哈希。

如果基线在新代码运行后才创建、只包含 chr10、或工具/输入不匹配且没有解释，先判为证据不足，不验收通过。

## 2. 判据表

| ID | 检查 | 通过标准 |
| --- | --- | --- |
| A01 | 修改范围 | 仅必要的 GPM Server/契约/测试/文档，无原版/其他项目顺带修改 |
| A02 | 算法接入 | 现有两轮 refill 后的末尾阶段，旧成功决策未重裁决 |
| A03 | 默认与 audit | off 的序列/有效成功语义等价旧版；audit 等价 off，无 donor 消费副作用 |
| A04 | 候选合法性 | 当前坐标、来源可追踪、同源同向同线性、受限窗口、无硬编码 |
| A05 | 准确性证据 | 全供体竞争、额外结构支持、两侧精细接头验证全部完成 |
| A06 | 成功保护 | 全部旧成功片段和接头逐项比较，改变/丢失项数为 0 |
| A07 | 非目标序列 | 全体新编辑之外序列逐碱基不变，不能靠全长哈希不同无法比较而跳过 |
| A08 | 目标 chr10 | 原 gap 已消失且替换有可信结构与来源证据；无新 gap/错误重复接头 |
| A09 | 坐标与重放 | 负向、多编辑、偏移、跨路径 N 正确；事件独立重建等于输出 |
| A10 | 报告/导出 | candidate/attempt/event/usage/path/FASTA 一致，证据可达，App/包契约通过 |
| A11 | 恢复与失败 | 模式切换与模块更改正确失效；中断不发布半成品；重跑确定性 |
| A12 | 负例 | 重复、真插入/供体缺失、保护区冲突、跨 gap、坏字段与工具失败均正确拒绝 |
| A13 | 下游稳定性 | Step4 和 q4 的已有端粒/成功片段来源与接头不被破坏 |
| A14 | 质量门禁 | 适用完整门禁实际通过，任何 skip 均已补齐而非当作通过 |
| A15 | 交付可重复 | commit/push/参数/哈希/命令/比较器齐全，另一个会话能重复结果 |

A08 未满足但输出 needs_review，不代表实现毫无价值；结论应为“工程实现可审阅，目标自动修复尚未完成”。不得写完整验收通过。
任何一项旧成功序列/连接丢失，或任何无证据的大删除，直接判验收失败。

## 3. Codex 审查步骤

### C1. 查代码，不先相信统计

- 对比基线与实现 commit，确认没有提高旧全局阈值替代新算法。
- 检查候选生成和判定是否有调查坐标/名称特判。
- 确认原成功片段与 guard 在精细切点确定后仍再次检查。
- 检查大删除证据能区分两组装差异与真实错装，未伪造 reads 或独立支持。
- 检查全 donor 检索、别名合并、secondary 截断处理和竞争分数。
- 检查新模块 hash、CLI 恢复白名单、.prepare_lib 分发，避免测试源码与运行旧副本错位。
- 检查异常、候选拒绝、审计 eligible、accepted、needs_review 的区别。

### C2. 独立复算 chr10

从输入按 source 坐标提取两侧序列和 donor，重新计算粗候选间隔与最终切点。
原始粗候选为 1,567,279 bp→9,529 bp，仅作为定位线索。最终值不同应能由精细比对解释。
确认长度变化公式：new_length = old_length - removed_length + inserted_length，并验证完整染色体与局部窗口两种尺度。
重新查看原始 MUMmer identity 列，不能使用被错读的原版字段。

独立检查三类证据：

1. 左右锚点和外侧同线性链真实存在，方向与切点正确。
2. 待删大片段确有重复/错位支持，目标连接并非仅一个供体的短缺失造成。
3. 完整 donor 集不存在同等级竞争解释；修复后两边接头没有重复/截短/新增 N。

如果证据无法判定，维持 needs_review 并要求补充数据或明确调整方案。不可为了验收把它作为 100 bp 普通 gap 放宽处理。

### C3. 独立核验“旧成功不变”

成功集合取 baseline 实际最终生效贡献，不按最新运行重定义成功集合，也不只比较数量。
对每项按 canonical source 身份关联，逐项检查方向、源区间、实际内容、顺序与左右 guard。
某成功结果拆成多个新 path 行时，先合并等价连续来源再比较；不能因行 ID 变化就认定回归，也不能因同名就认定不变。
成功区间外的旧原序列按 edit_map 对齐，逐碱基检查全部新编辑区间之外内容相同。

下游坐标平移是允许变化，但必须与累计净长度变化一致；不能把位于删除区的片段强行投影到边界上。
核验 Step4/q4/最终包，尤其已存在端粒结果和 chr06 控制例。
对新算法修复的其他 gap 一一检查证据，不接受未解释的“顺便变好”。

### C4. 重跑关键测试

Codex 至少独立重跑 T01/T02/T04/T05/T07/T11/T12/T13/T14，并核对其余与完整门禁日志。
不只跑实现者挑选的正例。对一个已有成功 gap 构造保护冲突候选，验证全部输出状态保持原样。
重放使用存档事件与源序列，关掉比对器后仍可重建相同输出，避免 replay 实际重新求解掩盖错误。

必要时在独立实验工作区重跑完整 gs2 apply。使用与基线相同环境，验证实际 prepared runtime hash 等于实施提交。
适用门禁参考 02-execution 和 QUALITY_zh.md。服务端纯代码不要求无关前端构建；如改动涉及前端/Rust，则按 Windows 规则验证。

### C5. 给出明确结论

结论只能是以下之一：

- **通过**：A01–A15 均有证据，目标可信修复，旧成功项改变/丢失数为 0。
- **未通过，需修正**：存在错误编辑、回归、契约失败、缺失完整门禁或不可重复实验。
- **证据不足，目标待解决**：工程测试可通过，但目标因歧义/输入缺失仍 needs_review，不宣称自动修复完成。

Codex 发现问题时给出文件/函数、复现、预期与实际。依用户已授权任务继续修正或交回 Claude 做具体修改，再重新验收受影响项。
不为修复重新询问已授权的普通实施权限；需要额外数据或实际权限时才明确说明缺失条件。
