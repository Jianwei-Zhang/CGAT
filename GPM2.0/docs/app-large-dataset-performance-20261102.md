### 方法与证据边界

- SQLite 使用只读连接和 `PRAGMA query_only=ON`；没有调用可能迁移数据库、保存参考分段或更新缓存的正常写入入口。

- 前端计时在 Windows Node 上调用本分支现有的真实模型/HTML 构建函数，输入为只读项目摘要、来源分片信息与已保存路径；后端依赖以这些数据替身提供。不是完整 Rust/Tauri 调用链。

- 第一次观察不等于系统冷缓存；本轮不据此推算端到端加速倍数或承诺秒数。
- 未启动浏览器/原生 App、未替换安装包、未改变现有项目。诊断前后数据库大小与 mtime 一致；这不是全文件 SHA-256 校验。

## 3. 已确认的代码路径与问题

### A. 项目页右下路径概览：小展示复用了重加载器

调用链：

`workspace-page.js` → `renderProjectPathOverview` / `bindProjectPathOverview` → `ensureProjectOverviewData` → `loadProjectExportData`。

`project-export-page.js` 的 `loadProjectExportData` 当前依次读取染色体、保存的视图状态、LGZ 基线，然后对每条染色体串行进行：

1. `listChrViewCtgs(datasetId: null)`：全部数据集。
2. `listChrViewCtgs(datasetId: primaryDatasetId)`：再次获取主数据集。
3. 开启分型时，`listPhasedChrTracks`，即使当前没有分型轨道。

真实前端加载器的只读数据替身测试记录了 **33 次调用**：3 次项目级读取 + 20 次 Contig 读取 + 10 次分型读取。这是该数据的需加载路径，不表示每次切页都会无条件重复 33 次。

两次 Contig 读取都未使用轻量模式。`main_view.rs` 的 `list_chr_view_ctgs_with_connection_options` 会逐 Contig 构建来源分片、命中、N 区域，主数据集还构建端粒/着丝粒标记；Tauri 随后将证据映射进返回 JSON。路径概览及总览统计代码没有消费这些命中/标记集合。

本数据中，两组读取共进入 **11,553 个 Contig 的命中读取流程**，其中主数据集被重复访问；SQL 读取得到 56,014 条命中行，合计约 120.7 MB 的 CIGAR 文本。这不是 IPC 返回量：当前接口不直接将原始 CIGAR 文本传给前端，但后端会读取并处理它们。

**结论：存在可证明的过度取数与重复构建。小预览应脱离完整装配证据通道。**

### B. 总览页：统计加载与完整预览是两条独立链路

- 统计部分沿用 A 中的重加载器。
- 完整预览由 `mountOverviewPreview` → `bindProjectPreviewPage` → `loadProjectPreviewData` 独立拥有；不能把它们合计为单条已测的串行耗时。
- 完整预览已具备内存、项目持久缓存、局部更新与 DOM 复用机制，不是“完全没有缓存”。
- 现场缓存为模型版本 8、修订 130；数据库当前修订为 134，identity 相同，10 条染色体均有高于 130 的 dirty 标记。因此这份缓存不能直接作为最新结果使用。dirty 原因本轮未归因，不将其判为缓存缺陷，也不以强用旧缓存提速。
- 当前冷读取 `readPreviewSources` 获取全项目来源；即使后续按 dirty 染色体重建部分卡片，也不等于来源查询已经按 dirty 范围缩小。
- 当前完整预览通过 `cards.map(renderCard)` 构建所有染色体、各数据集来源条、Final Path。真实摘要数据生成的完整总览标记约 **5.92 MB、24,115 个元素开始标签**；其中完整预览约 5.89 MB、23,572 个。标签数量是字符串计数，不是实测 DOM 节点数量，后者还包含文本节点等。
- `syncProjectPreviewSources` 在逐条更新位置/宽度后读取标签的 `scrollWidth/clientWidth`；这构成需要原生测量的布局风险，尚未量化实际强制布局耗时。

**结论：JS 模型计算不是目前唯一或最显眼的规模问题；需要优先量化大批 DOM 挂载、标签测量与首屏调度。缓存有效也不会自动消除这些成本。**

### C. 装配页：首屏等待范围大于主轨道本身

`assembly-data-runtime.js` 的 `loadAssemblyView` 已将部分读取并行化，并有请求代次检查，不能再笼统建议“加 Promise.all”或声称完全没有过期结果保护。

在首屏最终渲染前，仍会等待一组数据完成：主轨道、辅助轨道、分型轨道、参考成员、删除记录、历史状态，以及选中 Contig 的侧栏数据。侧栏数据又依次读取详情和编辑候选。

`list_ctg_edit_candidates_with_connection` 返回项目内除当前 Contig 外的全部移动目标。本数据一次选择对应 **12,741 个候选**。这是按需化候选的具体切入点，但本轮 SQL 单独读取约 25 ms，不能把它直接宣称为数秒卡顿的主因。

如果恢复了局部视图，当前还会在首次非 loading 渲染之前恢复其成对比对证据；这是为保证恢复状态完整而存在的顺序，不能随意拆掉后展示未标识的旧证据。

`assembly-page.js` 仍有整页 `innerHTML` 重建入口，同时也有局部替换入口。下一轮应逐操作记录使用了哪条渲染路径，而不是全盘推翻现有渲染系统。

**结论：装配页适合研究分阶段就绪、详情按需化、减少整页重建；真实主轨道构建、证据投影和原生绘制耗时仍待补测。**

### D. 公共来源读取存在逐 Contig 的查询开销

即使走现有 `previewOnly` 通道，后端也会为全项目每个 Contig 单独调用 `load_source_fragment`。多数不是分片，仍要执行查询。本数据 12,742 次分片判定在 Windows SQLite 诊断中约 582 ms。

已有 `previewOnly` 不能不加分析就直接替代总览接口：它固定读取全项目，并省略 `chrOrder`、派生目标等部分字段。新的轻量协议必须保留总览/导出实际需要的排序、筛选与来源语义。

## 5. 建议顺序：逐项确认、逐项实施

### 建议 1：共享轻量摘要通道（已实现，受控验证通过）

范围只覆盖项目页右下路径概览与总览统计，不改装配证据展示。

- 获取染色体、路径、主数据集统计及确有需要的来源身份/长度/放置元数据，不构建命中、N 区域或端部标记。
- 批量读取并建立项目级索引，避免逐染色体重复拿主数据集与全部数据集；批量获取分型元数据，保留空轨道语义。
- 两处展示共用按项目、内容修订约束的摘要，不另造彼此不一致的状态来源；是否新增持久缓存须在首轮测量后决定。
- 保留隐藏、派生 Contig 归属、跨染色体共分配、来源分片、反向、未分配计数与分型展开语义。不能简单按 `datasetId` 分桶替代当前完整筛选规则。
- 保留请求过期保护、错误与重试；页面切换后不得发布旧项目结果。

验收以展示/导出所需数据等价、调用数量与负载降低为核心；不承诺尚未实测的倍数。第一轮暂不引入 Canvas/WebGL、不改 DB 科学数据表。

### 建议 2：完整预览按可见染色体挂载

- 优先构建可见卡片与少量缓冲区；其余保留稳定占位，避免一次挂载全部来源条和标签。
- 模型/有效缓存仍代表完整项目；按需挂载只减少当下 DOM，不抽样或丢弃科学信息。
- 集中几何读取与样式写入，评估减少逐条标签测量；保留小间隔放大、来源高亮和参考偏移的显示契约。
- 导出图片单独使用完整模型，不把当前视口截图当完整项目导出。
- 保留滚动定位、染色体跳转、键盘/焦点、缩放和原生窗口尺寸变化行为。

本项先补原生分段测量再确定挂载策略；不会为了调查自动开启浏览器环境。

### 建议 3：装配页分阶段就绪与按需详情

- 先确定主轨道安全显示的最小数据集合；将不必要的侧栏详情、编辑候选移出首屏关键路径。
- 详情未就绪时明确显示状态，相关动作不可误操作；不展示上次选择/项目的旧详情。
- 按菜单实际打开再加载候选，或设计可检索分页；保留完整目标可达性，不静默截断前 N 个。
- 根据计时缩小整页重建范围；复用已有局部渲染能力，不重置无关视口、选择与用户编辑。
- 复核局部视图证据恢复，必要时独立标识证据加载状态；保留科学准确性和过期请求保护。
- 是否需要 Rust 异步调度、后台工作或真正可取消查询，由原生命令耗时与界面响应证据决定；JS 并行请求不代表这些成本已经解决。

### 建议 4：来源查询批量化与细粒度刷新

- 批量加载来源分片与共分配关系，消除逐 Contig 的空查询。
- 按 dirty 染色体及依赖范围读取来源，而不只是局部重建卡片。
- 只有契约变更才升级模型版本；保留 identity/revision 检查，不以放松缓存校验提速。

## 8. 第一项确认后的实现边界

- 新增项目级只读摘要入口：一批来源摘要、主数据集成员 ID 集合与分型元数据；来源摘要不构建或返回比对/端部证据。
- 前端保留现有共享 `projectExport` 状态、项目/内容变更保护和展示模型；不新增持久缓存或数据库迁移。
- 移除逐染色体的完整 Contig/分型请求，以项目级摘要和既有保存视图、LGZ 基线组成加载流程。
- 主数据集成员集合由后端按现有 SQL 筛选规则产生，不在前端仅按 datasetId 猜测派生归属。
- 来源分片逐项查询、完整预览虚拟挂载、装配页首屏拆分不属于本次实现。
- 项目级批量读取不再把所有来源 ID 重复拼进共分配查询的 IN 参数，避免来源数超过 SQLite 绑定变量上限；按染色体/数据集的装配查询保留原约束。此处是批量入口的容量边界修复，不包含来源分片查询批量化。


## 9. 第一项实现结果与验证

### 实现

- 新入口：`get_project_overview_sources`，Tauri 与开发桥/CLI 使用相同摘要协议。
- 路径概览与总览统计加载器现在调用：项目摘要 1 次、保存视图 1 次、LGZ 基线 1 次。本数据由 **33 次降为 3 次后端调用**；这不是完整总览页（含独立完整预览）的总请求数。
- 一次读取全部已分配来源摘要，后端明确给出主数据集成员 ID；前端按原顺序分组并复用对象，不再重复读取主数据集的完整证据。
- 摘要响应不含 `hits`、`nRegions`、`telomereMarks` 或 `centromereMarks`。保留来源身份、分片、派生归属、放置/排序、共分配与分型元数据。
- 保留原有展示函数、状态所有权、内容变更重试、过期请求与跨项目保护；没有新增持久缓存、迁移、UI 样式或科学算法变更。
