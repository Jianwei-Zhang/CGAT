# 远端 Server 长任务：定点修复与续跑规范

本规范记录用户在小麦任务中的明确授权，防止换会话或上下文压缩后退回“等失败、重装整版、全量重跑”的处理方式。

## 1. 适用范围与授权

- 当前适用于 SSH `180` 上的小麦新旧版对照任务，以及用户明确要求沿用本规范的远端 Server 排障。不能据此操作其他项目或主机。
- **新版不仅失败可以修：确认存在异常耗时、重复计算或可省略的流程时，可以直接定点修复并按需重提，不必逐次等待用户批准。**
- 用户没有要求多节点改造。继续单节点 x86 路线；不要另开多节点工程。
- 旧版作为对照，默认只监控、不修改、不主动中止。发现旧版异常需报告；修改旧版需要单独授权。
- 后来的明确用户指令优先。集群访问、数据保护、生产操作及 Git 权限要求仍然有效。

## 2. 什么情况触发排查与修复

| 现象 | 核实内容 | 允许的处理 |
| --- | --- | --- |
| 异常退出、断言、缺失依赖、OOM | 调度器终态、退出原因、当前 run 的日志、进程与输出证据 | 定点修复后从有效结果续跑 |
| 长时间单核或低 CPU 占用 | 连续采样、输出是否增长、线程实际分配、I/O/内存压力、具体代码路径 | 确认可避免的串行瓶颈后优化，不必等失败 |
| 所需信息已经完整存在 | 来源、输入/参数/工具身份、完整输出和成功标记 | 验证后跳过计算 |
| 部分结果存在 | 哪些子任务已完整提交，哪些只有临时/不完整结果 | 复用完整部分，只补缺失或失效部分 |
| 重复扫描、重复校验、重复执行 | 调用链、重复次数、是否存在有效缓存和并发访问 | 删除不必要的扫描或提前快速排除，保留最终完整性验证 |
| 内存逼近硬上限 | 调度器真实限制、进程并发、单任务峰值和余量 | 收紧进程并发、调整计算线程，必要时增加内存配额后重提 |

**低占用、日志安静或单次输出不增长不是立即取消的依据。** 长序列批处理可能先计算后集中写出。先区分正常长尾、I/O 等待、真正停滞和重复工作；观察超时/SSH 断开也不等于作业失败。

不要设置一个不看阶段和数据规模的统一“等待 N 分钟就杀掉”规则。采样告警只触发检查，不自动证明必须重启。

### 长序列并发与内存边界

- 小麦已出现“最多两个比对进程仍顶满 240 GiB”的 OOM；不能把进程数上限当作内存安全证明。
- 当前 RSS、单条已完成查询的低峰值、增加到 320 GiB 配额，都不足以授权其他超长查询并发。必须区分组装间比对、自比对、目标规模和重复复杂度；未验证的长任务继续独占。
- 快速参数降低某个样本的内存，不自动触发四路或两路长任务并发。内存预留数字只是调度启发，不是对 mapper 的硬限制；扩并发必须另有同类任务峰值与总余量证据。
- 独立诊断试验的时间预算不能冒充主流程超时策略；试验超时只说明该候选尚无完整结果，不等于主任务失败，也不能采用它的临时输出。

### 队首阻塞修复不改变证据消费顺序

- 规划池和 mapper 池均检查“按提交顺序等待”是否让已完成任务无法回收补位；不能只修其中一处。
- 可以按完成顺序派发、回收，但每个父查询必须先完成整组区域/原生回退判定；最终区域任务、回退分组、组内查询及报告列表都恢复原始顺序，再交给下游消费。不能边完成边修改科学 catalog。
- 保持原有有界预取、总 CPU/内存预算、地址空间保护和精确 owner 重算；资源故障不丢父查询，内容错误仍失败。保留 FIFO 接口供需要即时原序的调用方使用。
- “少算工作”优化先实样核对最终目标/窗口/base 是否真的减少，不能只因源码尚未传 selection 就认定大量重复比对。若仅少解析少量随后本来会丢弃的记录、实样无目标缩减，不为理论收益加入复杂缓存迁移或拖延已验证的修复。改变窗口/目标集合前优先保住已有完整 raw/project 命中；参考坐标投影不冒充精确 contig 间 CIGAR。
- 以延迟队首、乱序完成、交错回退分组、单 CPU 不重叠及真实 spawn 等价测试验证。实样规划倍率只代表规划，不冒充原生比对或整套任务提速；切换前仍要评估续跑验证与已完成结果再读取的成本。

- 需要量化 mapper 回收收益时，用完整窗口FASTA的原SHA、同工具/原参数/原guard/相同路数做有界原生对照，并核对完整stdout；A/B/B/A可减小预热偏差。规划倍率、服务时间回放和原生子步骤倍率都不是整套倍率，不能相乘宣传。控制器没有生产DNA大堆时，也不冒称覆盖真实大堆的fork成本。
- 判断是否值得再次续跑时，不只看planned减completed：先核对完整native矩阵能覆盖的父查询、可能跳过窗口的保守界和已完成结果；整父查询fallback可能替代多个窗口。保留这些限制，不能把窗口数说成独立minimap2进程数，亦不能把诊断验证当作主流程已经应用补丁。

### 续跑后的资源池与进度判读

- 先区分参考/assignment完整性验证、已完成leaf复用、受保护普通池、快速池和独占任务。普通池扩并发不会自动放开其他池；看到一条mapper不能直接断言新调度未生效。核对真实命令、任务规模、池准入条件及待运行优先级。
- 连续短任务正在完成且普通池即将进入时，不要仅为立即展示更多并发再中断、再次支付续跑校验成本。若仍有持续低效或长尾，则按上面的证据标准排查，不用这条规则掩盖真正的串行瓶颈。
- `run_all.sh`线程数是总预算，不是每路和路数都取同一个值。记录实际各路线程之和、CPU与内存；例如7路分配8+4+7+1+3+5+4=32并已用满约31核，不应为了凑32路而超售。历史缓存复用数量、此次新增成功数量、guard实际执行receipt要分别报告，不能把符合新池资格的旧结果追认为已受新guard保护。

### 区域规划与 mapper 共享单节点预算

- 规划进程只能接收源分段元数据、窗口和已验证只读索引；使用 fresh `spawn`，不从携带整套 DNA 的进程 `fork` 后再套小地址空间上限。部分覆盖补比对和候选染色体两条路径采用同一执行器。
- `run_all.sh` 的线程数包含主进程、规划和 mapper 的总预算。32线程、内存足够时的上限是主进程1 + 规划3 + mapper14×2，不是32路各32线程。单线程时也不能让主进程规划与 mapper 同时计算。
- 扩池需要当前作业的内存硬额度证据。若 cgroup 上限不可读，可由正常资源 ready gate 转交 SHA 绑定的 `djob` 凭据；实际 reader 必须核对当前主机、账号、单节点、CPU/内存额度及自身 cgroup 的 job ID。不得相信任意环境变量中的内存数字，也不以节点总内存或当前低 RSS 代替硬额度。不具备凭据时维持串行规划和最多4路 mapper 的保守路径。
- 预算包括主进程峰值、后续增长余量、每个规划进程8GiB AS、每个 mapper 4GiB AS及主进程端提取/解析余量、有界预取/返回计划。AS 是单进程虚拟地址空间限制，预留数字不是整棵进程树的 RSS 证明，仍须监控实际作业内存。
- 原始 PAF 和本地镜像先由正常 owner 完整验证。worker 只继承本次存活 owner 的元数据与稳定文件身份，自己打开 SQLite/文件句柄，并继续逐条核对记录 SHA；不为每个 worker 再扫描整套 PAF，也不把这份内存中的委托对象保存为下次续跑的内容凭据。数据库生命周期、绑定、原始 PAF 和镜像都须有漂移栅栏。
- 按原顺序消费有界预取结果；完整父序列的回退决定必须先完成，不能先映射前几个窗口再漏掉后续。规划进程资源不足、损坏或返回计划过大时，在 owner 中重算同一个精确计划；输入/记录身份错误必须失败，不能当成资源回退而吞掉。原生全长回退仍在区域池全部退出后独占运行。
- 先用隔离的真实窗口比较完整坐标、顺序与回退决定，再评估包含启动/退出成本的耗时。不把规划阶段的倍率或受控样本的低内存推成整套小麦倍率、未经测量的全长原生并发许可或已部署事实。新源码须纳入 builder identity 并按独立 transition 安装，不热改仍在运行的冻结 bundle。

### 大量区域窗口：先验证策略收益，不只减计数

- 窗口计数、目标bp、旧PAF静态保留率与实际运行时间分别报告；不能把目标量减少当作同比提速。
  粗筛后重建较小target index也可能让某些重复区域精比对更慢，必须用同节点、同工具的真实
  原生控制比较包含粗筛/文件准备/精比对/验证的耗时，并独立查看最慢个例。
- 需要减少工作时，依次查完整历史矩阵可复用范围、短名单、批量查询/共享目标index与条件触发；
  不能把四个supplemental矩阵当成全部初始self/cross证据，也不能把矩阵成员重叠直接当作
  精度/profile/窗口上下文等价的负结果。没有证明的范围不补写“精确无命中”成功凭据。
- 科学筛选、重复seed阈值和batch目标上下文变化，均不能伪装成资源-only/AST等价迁移。
  旧完整raw先复用；近似工作的选择依据、遗漏范围、真实原生输出和消费者闭包须独立绑定。
  损失按旧区间减新覆盖的差集统计，新获得区间另计，不能用净增覆盖掩盖丢失；区分intra/cross
  和个例尾部风险。已完成窗口试验不替代held-out/长尾或整套最终结果验收。
- 粗筛保留全部链与精比对延伸全部链是两项独立选择。核对实际mapper版本的参数交互：
  minimap2保留`-P`时增加`-p`/`-N`不能限制secondary；`-N`也不是全PAF严格N行。
  若改精比对链准入，保持完整旧结果身份，分别验证intra/cross及每窗口局部损失；不能只看
  覆盖加权均值或把新获得的区间抵扣丢失。较弱科学档仍需独立样本/长尾及消费者身份检查。
- 候选实测更慢时保留失败/负收益证据、不切主任务；改测下一种策略，不为了展示优化反复中断续跑。

### 只读诊断的访问边界

- 直接 SSH 到计算节点若因缺少可信主机密钥而失败，不关闭 host-key 校验、不改认证/路由，也不把这个失败当作主作业失败。
- 需要进程级证据时，可以在集群规则允许的范围内，通过已认证调度器提交同节点、低资源、短时的只读诊断作业；先检查节点余量。只采样当前用户、目标工作区的进程，不读取其他用户的数据，不改主任务。
- 线程 CPU 时间持续增加可证明线程仍在执行，但不等于比对结果持续推进，也不能替代函数级瓶颈定位。结合输出和已有批次耗时判断。
- 诊断工具缺失或权限不足时停止该采样方法；不自动安装系统工具、不使用 sudo、不修改 perf/ptrace 安全设置。诊断作业失败与分析主作业失败必须分开报告。

## 3. 定点修复的最小闭环

1. **确认目标与状态**：读取适用 AGENTS/远端 skill；检查 SSH alias 配置；核实主机、工作区、调度器 job ID、运行版本及当前 run ID。
2. **保存证据**：记录失败/低效位置、资源采样、输出增长、相关日志及已有成功检查点。区分当前失败与日志里的历史失败。
3. **定位根因并检查同类问题**：追踪调用者、下游与同类模块；检查安装目录和工作区内嵌工具是否存在同样问题。不是只修报错的一行。
   - 改变执行身份、缓存或检查点解释时，同时审查**生产者、续跑控制器、下游证据读取器、打包/报告消费者**。只让 writer 成功提交，不等于独立进程中的 reader 能验证它。新增参数身份必须显式验证，不能删掉字段或伪装原生结果；优先在上游长任务结束前用微型回归复现边界问题。
4. **选择最小改动**：优先不改变科学结果的性能修复、资源调整和安全复用。只改必要文件/函数，不混入当前 master 的新功能。
5. **备份与定向验证**：保留旧文件、SHA-256、补丁范围、来源提交、针对性测试结果及回滚方式。导入真实模块验证，避免测试人工注入缺失依赖而掩盖错误。
6. **决定原地生效还是重提**：见第 4 节。若重提，确认原作业及其子进程已停止、正常工作区锁已释放；不得偷锁、并行写同一工作区。
7. **验证实际恢复**：检查新 job 已运行、资源限制生效、日志确实复用了指定结果，并有新的有效计算/产出。提交成功、目录存在或监控锁文件不等于恢复成功。
8. **保存到仓库**：已验证的通用修复定向提交并推送，不能只留远端。暂时仅适用于事故的包装脚本也要在交接记录中列出，不能称为“已经全部进入 master”。

## 4. 什么时候重提，什么时候不打断

- 正在产生有效结果、修复收益不足以抵消损失时，先保留计算，不为部署一个小优化而机械重启。
- 已确认长时间无效计算、重复步骤或资源配置必然失败时，可以主动修复重提，不必等进程崩溃。
- 仅修改未来步骤，也必须检查代码是否已加载、是否被当前阶段的输入指纹绑定。**“还没执行到这个脚本”不代表可以安全热替换。**
- q0 染色体比对的外层检查点会再次核验执行前捕获的输入/工具身份。中途修改相关 helper、manifest 或 command 可能使收尾失败；不能通过删除核验绕过。
- 对经过等价性验证的代码变更，可以显式迁移检查点：仅允许列明的代码身份差异，其他输入、参数、工具及全部输出必须仍一致；保留迁移前检查点和迁移凭据。
- 已执行进程通常不会自动加载磁盘上的 Python 修复；必须核实真正运行的代码，不能把“文件已上传”当成“修复已生效”。
- 近似参数或不同执行路径不能冒用原参缓存身份。若采用隔离执行替换而不改原命令，叶子与外层检查点都必须绑定实际执行脚本、代码、策略和结果回执；保留阶段收尾重新捕获输入的核验，不得只因适配层与原检查器不兼容就跳过它。

## 5. 结果复用与校验精简

### 必须保留

- 已完成的初始参考比对；不得因小修复无声重跑。
- 有完整性证据的染色体分配、组装间比对、自比对批次及后续阶段结果。
- 输入/参数/工具来源与输出内容的对应关系、输出格式/坐标检查、必要的最终内容校验。
- 临时失败数据与诊断日志；不能随手清理工作区、cache 或重新 prepare。

### 可以精简

- 在内容身份不变的有效作用域内复用已经验证的摘要；文件变化、来源不确定或缓存失效时回到完整验证。
- 已知后续批次缺失时，先用小型完成标记判断“不能合并”，不要反复读完整个已完成前缀；全部到齐后仍完整校验再合并。
- 自比对续跑时，优先由父控制器核验并复用已完成批次，避免为每个缓存命中启动 helper、重读派生索引或重复合并同一组。原始 query/target/tool 和结果内容身份仍必须核对；每组最后一个成功回调提交前再确认完整合并。普通批次和快速批次都应覆盖，而不是只优化近似分支。
- 完整子任务具备可信成功退出、输入/工具身份及输出校验时，建立更细粒度的复用记录，不必等整条染色体全部结束才能保留成果。
- 单纯运行路径、环境标签、资源预算等变化是否应失效，要按真实语义判断，不应一刀切重算。

**不可把“文件存在”“非空”“mtime 一样”或孤立的一行成功日志当成充分成功证据。** 不完整 PAF、未提交的 batch、被 OOM 中断的结果不能作为完整缓存接纳。检查点缺失也不自动证明已有结果不可用，需要做有来源约束的补充验证。

## 6. 性能、资源与允许的精度折中

- 用户允许大数据场景适度牺牲精度换速度，且触发判断应由程序内部完成，不应让用户手动判断是否属于大数据。
- 2026-11-19 用户再次明确：超长序列可以降低精度以明显提速。不能把几乎逐条复现全部重复/次级命中的门槛当成唯一可接受目标，也不能为每个长查询另跑完整慢基线。优先复用已有结果、做有时间上限的小对照；分别记录主要位置、长且高相似度片段、重复/多重命中的变化。`tp:P` 或高相似度本身不是正确性证明，下游可能使用次级命中，必须核对真实消费路径。具体可接受损失尚未被量化，不能将“大量主要关系丢失”自行解释为用户已接受。
- 这是一项授权/设计要求，**不是所有近似优化都已实现或已经获准无条件启用**。触发条件应有实际数据规模、重复度、内存或耗时证据；记录使用的参数、算法路径和输出语义变化。
- 优先精确等价优化。若确实采用近似路径，不得冒称输出等价；要保留可追溯信息及必要的完整算法回退，说明对新旧版结果比较的影响，不能静默改变旧版基线。
- CPU 线程预算、同时运行的比对进程数、调度器 CPU 申请和硬内存限制是不同概念；必须分别检查。一个任务内部多线程仍可能消耗大量内存。
- 资源调整按实际队列规则和空闲资源进行，不能把某次“小麦申请 24 核、实际用 16 线程、最多 2 个比对”的措施固化为所有数据的默认值。
- 不凭 `dmod --help` 推断运行中可以扩容。先查适用规则，必要时用独立轻量作业验证；命令退出码为 0 仍可能逐作业修改失败，须检查返回明细与调度器实际分配/硬限制。2026-11-19 的 Donau 小麦诊断已确认一次运行中 CPU 增加请求被拒绝，不应在主任务上赌这种操作能救 OOM，也不能仅提高 `-RL` 绕过每核内存规则。
- 不把合成数据微基准的倍率说成整套小麦任务的加速倍率；旧新版阶段顺序不同，不能仅凭 step 编号或 CPU 使用率判断谁整体更快。

## 7. 不走每次发布的大循环

- 当前用户要求：**先让完整任务跑通，期间现场定点修复；最后再处理正式版本发布。**
- 每次修复采用轻量源码审阅、针对性测试和远端真实续跑验证；不自动运行整版 CI、不更换整套安装、不执行 `update.sh`、不重新 prepare、不替换 Release 资产、不发布 docs 网站。
- 已验证改动仍需定向提交/推送，并记录源码与远端补丁对应关系；使用 `[skip ci]` 避免把事故处理变成重复发布。
- 将来真正发布时，仍执行 `RELEASING.md` 的正式门禁。这里免除的是事故处理时的反复发布，不是永久豁免发布验收。

## 8. 压缩/换会话后的接续顺序

1. 读本规范与 `wheat-remote-handoff-20261118.md`；不要从旧聊天推测最新 job ID。
2. 查远端调度器、最新提交凭据和当前日志；交接快照必须重新核实。
3. 核对当前 runtime SHA、事故补丁目录、检查点迁移与复用记录；确认哪些修复已经进 master、哪些仍只在远端。
4. 先观察再动作：不要重复提交、重新 apply 补丁、盲目运行旧启动脚本或重启仍活着的监控进程。
5. 持续监控不等于后台脚本能自动修复或主动向聊天发通知；明确区分只读采样、当前代理的实际处理和已经验证的任务完成。

### 小麦两路 self 的资源保护与复用

- 历史两路 cross OOM 不代表所有 self 都必须永远串行。相反，少数低RSS样本也不能
  直接推导无保护并发安全。当前两路试行需要完整self峰值证据、明确单进程地址空间
  上限、失败不提交成功标记、原子结果复用，以及真实调度器320GiB硬额度。
- RLIMIT_AS约束的是每个进程的虚拟地址空间，不是整棵进程树或作业RSS。当前快速
  任务64GiB上限，最多两路、各预留128GiB，不和native池混跑；cross/unknown继续独占。
  超出保护上限后应诊断具体失败并考虑有证据的串行/资源回退，不能盲目取消保护。
- 仅改资源时复用原科学profile、原batch key与完整产出，通过新资源overlay绑定

### 放宽自动快速档时保留旧执行身份

- 大数据内部 self 的自动触发阈值应根据真实慢任务评估，不能把100Mb当成永久性能分界。
